What a week of building on the Workbench API taught us

From October 5 to 12, 2026, one Unity 6000.3 URP project was built against the staging Pipeline API: an asset explorer, branch comparison, a browser level editor, Blender round-trips, a whole-scene WebGL viewer, and publishing back to git. This report covers where the APIs were slow, where they took too many calls, where they surprised us, and how the Scene Preview samples held up.

Project: pipeline_sept26_test · Unity 6000.3.23f1 · URPData: 512 timed archive requests, about 27k workbench polls, and the session transcript

Summary

Writes are fast: a commit lands in about 1 s and validates in about 12 s. Reads at a validated revision are fast too. The time goes to imports (one in six archive requests took longer than a minute), to waiting without signals (everything is polled), and to workarounds for behavior the API doesn't announce: a sync that doesn't sync, a branch name that reads back as main, a publish that fails with raw git stderr. The five changes that would help most:

  1. Make imports asynchronous. Return 202 with a job or Location and progress states (queued, starting Editor, compiling shaders). Don't hold a synchronous POST open for minutes.
  2. Push state changes. Webhooks or SSE for "revision validated", "import done" and "publish done", plus ETags on head, would replace tens of thousands of polls.
  3. Make sync pull new commits, and expose the git branch. sync should fast-forward to the branch head, and GET should return gitBranch. Today every new commit means a new workbench.
  4. Collapse the common workflows into one call each: a single multipart commit, and an import-and-download by path.
  5. Version the API and return specific errors. The shape changed four ways in three days. Return clear 4xx codes (no_vcs_credentials, project_service_stopped, importer_not_in_revision), never a generic 502 or gateway 404.

Where the time went

  • Imports block a connection. The first import at a revision starts an Editor and imports the asset. A scene import also compiles every shader variant its materials need. Every client has to wrap the POST in a resend loop and guess at timeouts.
  • Cold starts aren't flagged. After an overnight idle, workbench reads returned 519 × 503 status_authority_unavailable instead of saying the service was stopped. A status of starting with jobStatus: Succeeded actually meant stopped.
  • Creating a workbench takes 3 s and gives no handle to wait on. The client then polls head for minutes.
  • Polling volume. About 27,000 workbench polls over five days, each one two upstream calls (GET workbench + GET head). Some of that was the explorer's own fault: 3,846 polls hit workbenches that had been deleted. Most of it, though, exists because nothing tells a client that a revision is ready.

Fewer steps

Counted from working client code. Each flow's suggested replacement is underneath it.

Edit one file and save it as a revision 5+ calls, then polls

md5(file)                          (client)
PUT  …/blobs/{md5}                 → uploadHandle
GET  …/files tree                  (per missing folder level)
POST …/transactions {"branchName":"main"}
POST …/transactions/{tx}/assets    [{path, uploadHandle}]
PATCH …/transactions/{tx}          {"status":"committed","message":…}
GET  …/head  … until validatedRevision moves

Better: POST …/commits as multipart (files plus message) that returns the new revision and an event when it validates. Abandoned transactions also have to be DELETEd by hand today.

Asset path → content archive 3–6 calls

POST …/asset-guid {"paths":[…]}    (no leading "/", unlike file-tree paths)
GET  …/environments                (first time: profiles + create environment)
POST …/environments/{env}/revisions/{rev}/imports {"importAddresses":["T:{guid}+{Importer}"]}
     … resend until a manifest comes back
GET  …/imports/{address}?artifactName=.ca

Better: accept paths in import addresses, add ?download= to return the named artifact when the import finishes, and pick or create the environment from a profile name.

Start working on a branch ≈ 7 calls, then polls

GET  projectservice/status → POST projectservice/start → poll
POST …/workbenches {type, repo, branch, name, vcsConnectionId}
GET  …/head  … until validated   (+ GET workbench for validation errors)
GET  …/profiles → POST …/environments

Better: start Project Service automatically on first use, return 202 plus Location from create, and include validation errors in head.

Compare two branches ≈ 3 calls per side, plus git

git ls-remote                      (the API can't say which branch a workbench is on)
GET …/head, GET …/files, GET …/assets/{guid}   per side

Better: expose gitBranch and upstreamRevision on list and get, and add a revision diff endpoint.

Also: an asset detail view took 4 calls (guid, asset, meta, file). Path segments need / encoded as %2F. The main artifact needs ?artifactName=., because an empty name returns the manifest again.

Surprises and errors

These are ordered by how much time each one cost.

Sync reports success but doesn't pull new commits

PATCH …/workbenches/{wb} {"type":"sync"} answers {"status":"validated"} in about 1 s, but upstreamRevision doesn't change. One workbench stayed on 6adde27 while main was at 844f8b2. So every pushed commit meant a new workbench, a new cold validation and new environments.

Make sync fast-forward to the branch head and return the new revision, or reject it with an error that says what it does.

The API changed shape four ways in three days, unannounced

Between October 5 and 7:

  • /branches/{b}/projectservice/* moved to the project level.
  • readiness became head {settledRevision}, then {validatedRevision, validating}.
  • Fields were renamed: keys to paths, addresses to importAddresses, and isFolder to type:"folder".
  • /batch gave way to transactions, environments moved to project level, and previews went from POST plus job to a GET that returns 202.
  • The workbench list changed from {items} to {workbenches} and lost branchName, createdAt and owner.

Removed routes returned a generic gateway 404 (code 54), which looks like "resource not found".

Use versioned routes, a changelog, Deprecation/Sunset headers, and a distinct "route not served" error.

A workbench forgets its git branch

The create response says "branchName":"demo-123", but GET on the same workbench says "main" (its internal branch). Two workbenches lost their branch this way. A create request that the client gave up on (499) still created a workbench, and its branch could never be recovered.

Return gitBranch on get and list, and make create idempotent with a client-supplied key.

Publishing without a VCS connection fails late, with raw git output

The publish returns a 502 backend_error containing could not read Username for 'https://github.com' after about 4 s. A connection can't be added to an existing workbench, so the work had to be redone on a new one.

Reject the publish up front with 4xx no_vcs_credentials, and let a connection be attached later. Document that vcsConnectionId is a Build Automation connection ID.

Published branches start from an old commit

Publishes go to pr-{commit} branches based on the commit the workbench was created from. One workbench produced three stacked pr-* branches in about 40 minutes. Merging them conflicted in a scene and brought back seven prefabs that had been deleted on main. One early publish went straight to main (git push origin pr-X pr-X:<branch>).

Reuse one branch per workbench, offer a rebase onto the current branch head, and document when a publish is drafted (409 publish_drafted) and when it pushes directly.

"Type not found" doesn't say which commit it compiled

import_failed: Type not found for scriptedImporterTypeName='…PreviewSceneImporter'. The importer had been pushed, but the workbench predated it, and the sync above couldn't bring it in.

Include the compiled revision in the error, and suggest creating a workbench from a commit that includes the importer.

Smaller inconsistencies

  • File-tree paths start with /, but asset-guid paths must not.
  • Transactions require branchName:"main". The git branch name fails.
  • Token expiry seems to come back as 403, not 401 (118 × 403 near expiry; not confirmed). Off VPN, calls return an HTML 403 page.
  • A workbench can hold only one open transaction, and an abandoned one blocks new ones until it times out.

Auth and adjacent services

  • Tokens. The Pipeline API takes a dashboard JWT copied from browser devtools, valid about 72 hours. There is no service-account or PAT flow for tools.
  • Collaboration needs a different token. It rejects the pipeline JWT. A Genesis token has to be exchanged first at /api/auth/v1/genesis-token-exchange/unity, and without that the error is Jwt is not in the form…. The Genesis token stopped working within about an hour.
  • Comment target format. The SDK's AssetReference builds assets/projects/…, which saves but doesn't show in the dashboard. unity/project/… passes search but fails on create (41503). Only unity/projects/{p}/assets/{guid} works everywhere. Thumbnail upload needs an undocumented x-ms-blob-type: BlockBlob header.
  • VCS connections. Build Automation v3 has no create operation. The internal v2 create returned 422 Repository URL is not reachable: Git ls-remote failure for GitHub over HTTPS, even for a public repository with no credentials. Only an OAuth connection made in the dashboard worked.

Suggestion One token for every Unity Cloud API a pipeline tool calls, a documented service-account flow, VCS connection creation in the Pipeline API, and one canonical asset-reference format shared by the SDK and the service.

Scene Preview samples

The samples ship the asset-level path: a scripted importer turns one asset into one content archive (.ca), and a player downloads, mounts and shows it on an orbit camera. That core is well designed:

  • The loader uses two slots, so a new preview swaps in cleanly.
  • It never reuses a mount prefix, and it tears down in the right order.
  • GlobalTableDependency handles built-in resources.
  • The AGENTS.md list of rules was useful.

Getting it to run against staging, and on WebGL, took a lot of work.

What had to be built on top

  • Whole-scene archives. Scenes need the parallel API path (CalculatePlayerDependenciesForScene, WriteSceneSerializedFile, LoadSceneAsync), two content files, and a manifest that records dependency order. Nothing in the samples covers it.
  • A stage around previews: sky, trilight ambient, linear fog, and props that move away from large assets.
  • Comments stored as Collaboration annotations, including a link.xml for its reflection-based models.
  • A multi-archive loader for the level editor. The level editor copies the loader's mount code instead of reusing PreviewLoader, because that only holds one archive at a time.

Rendering pitfalls the samples don't warn about

  • Pink materials on WebGL 2. The art uses shader model 4.5. The fix was WebGPU first with WebGL 2 as fallback, plus a new workbench, because archives are compiled for the commit's graphics APIs.
  • Grass in flat fog color. Shaders that URP looks up at runtime come from the player, and an empty player scene strips their fog variants. The fix was custom fog stripping that keeps all three fog modes.
  • Black-and-white scenes. Skybox ambient isn't computed for scenes loaded from archives. Trilight or flat ambient works. This is still unresolved for SampleScene.
  • One-byte-short reads. The archive file system can return small files one byte short. Both the sample and the scene importer pad their manifests to survive it. This is a platform bug with a workaround, not a fix.
  • Scripts can't travel in archives on IL2CPP. Gameplay code has to be in the player and kept with link.xml.

Iteration cost

WebGL player builds took 25 to 40 minutes, and Brotli alone took 8 to 10. The build profile's compression field turned out to be LZ4 data compression, not WebGL compression; the setting that matters is Player Settings > Publishing Settings > Compression Format.

Suggestions for the samples

  1. Ship a scene importer and scene loader next to the asset ones, with the dependency-order manifest.
  2. Fix the short read in the archive file system, and until then make the manifest format robust to it by default.
  3. Make PreviewLoader reusable: events, several archives at once, public bounds, and an "unload all".
  4. Use the Input System, ship the art inside the package instead of in LFS, and include a host-page bridge and embedded mode.
  5. Ship WebGL profiles: release builds, WebGPU first with WebGL 2 as fallback, compression off for local serving. Leave TLS/Curl out of the link.xml generator.
  6. Default the setup to trilight ambient and custom fog stripping, or warn when a loaded scene needs variants or lighting the player stripped.
  7. Replace reflection on internal APIs with public ones, and keep the client in step with the current routes. Test the samples against staging in CI.

Method and caveats

  • The durations come from about 40 explorer server logs (ASP.NET "Request finished" lines). They measure the explorer's endpoints, which may wrap several API calls and resends, so they are user-facing waits rather than single-call latencies.
  • Scene and prefab imports couldn't be told apart in the logs. A local Editor build of one scene archive took 50 to 90 s, which gives a sense of scale.
  • Cold start, workbench validation and preview times marked with * are estimates from timestamps and in-app hints, not timed measurements.
  • Some of the polling volume came from the explorer's own polling design, not from the API.
  • All of this is against staging during a period of active API change. Production may behave differently.
